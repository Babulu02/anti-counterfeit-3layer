# Known Limitations

This file documents honest limitations of the prototype. These are important to state clearly
in any paper or presentation.

---

## L-001  NFC is emulated, not physical

The NFC identity layer (Phase 2) emulates NTAG 424 DNA behavior in software.
No physical NFC chips are read or written. Consequences:

- The counter is stored in a database, not in hardware. A real NTAG 424 DNA stores the counter
  in tamper-evident hardware memory — an attacker cannot reset it without destroying the tag.
- In the emulation, a sufficiently resourceful attacker who clones the database state could
  replicate the counter. This is noted in the attack model.
- The Web NFC option (Phase 6) uses the browser's experimental Web NFC API (Android Chrome only).
  It is not available on iOS or desktop browsers as of 2026.

---

## L-002  Scan data is entirely simulated

All ML training and evaluation data (Phase 4) is generated by `experiments/simulate_scans.py`
with configurable attack mixes. Consequences:

- Reported precision/recall/F1 numbers reflect performance on synthetic data, not real-world scans.
- Real scan patterns (e.g. seasonal demand, regional distribution chains, device fingerprinting
  accuracy) may differ significantly from the simulation.
- All outputs from `run_all.py` include a header line: "NOTE: all data is simulated."

---

## L-003  Attacker adaptation

The ML model is trained on specific, labelled attack patterns (impossible travel, burst, slow clone).
A sophisticated attacker who knows the model can adapt:

- They could time cloned scans to avoid impossible-travel detection.
- They could use many distinct devices over a long period to evade burst detection.
- The NFC counter check is the strongest defense against replay; the ML layer is a second line.

---

## L-004  Privacy of location data

The system collects scan latitude/longitude to detect impossible travel. This creates
a geolocation trail per scan event. Mitigations implemented:

- Raw coordinates are never stored on-chain (only a hash, see DECISIONS.md D-007).
- The MySQL database stores raw coordinates; in production it should be encrypted at rest
  and subject to a retention policy (e.g. delete after 90 days).
- Users scanning products are not explicitly consenting to location tracking in this prototype.
  A production system must comply with GDPR / local privacy law.

---

## L-005  MetaMask is optional

The frontend supports MetaMask for manufacturer signing but falls back to backend-signed
transactions if MetaMask is not installed. This means product registration can happen without
the manufacturer's private key if an attacker compromises the backend. In production, all
`registerProduct` calls should be signed by the manufacturer's own wallet.

---

## L-006  Image-consistency signal (Phase 8): Threshold calibration, frozen accuracy, and backbone comparison

The visual consistency signal compares uploaded scan photos against registered reference images using cosine similarity and Platt scaling. In evaluation on the Stanford Online Products (SOP) dataset (`Ebay_test.txt`, product-disjoint from training split `Ebay_train.txt`):

**MobileNetV2 (1280-d ImageNet Pretrained):**
- Overall ROC-AUC against all impostors: **0.9115**
- ROC-AUC against random impostors (different category): **0.9574**
- ROC-AUC against hard negatives (same superclass, different product class): **0.8656**
- FAR @ FRR = 5%: **0.4747** (threshold = 0.2385 on test; operating threshold = 0.2402 on validation)
- Platt scaling reduces Expected Calibration Error (ECE) by **62.24%** (from 0.1337 down to 0.0505)

**Root Cause of the Initial 0.5013 Frozen Accuracy:**
In initial experiments, frozen decision accuracy was reported at **50.13%**, appearing inconsistent with the strong ROC-AUC of 0.9115. Root cause analysis revealed an asymmetric thresholding bug:
- The genuine threshold was selected at $\tau_{gen} = 0.2401$ (FRR 5%), but the counterfeit threshold was set via an arbitrary heuristic $\tau_{cnt} = \tau_{gen} - 0.20 = 0.0401$.
- Because impostor cosine similarities on generic visual features have minimum similarity $\sim 0.0425$ and mean $0.238$, **no negative pairs ever fell below 0.0401**.
- Consequently, 100% of non-abstaining pairs were predicted as genuine ($1$), collapsing accuracy on a balanced test set to exactly 50.13%.
- Selecting thresholds symmetrically on the validation split from the ROC curve (counterfeit at validation FRR $\le 5\%$ ($\tau_{cnt} = 0.2402$) and genuine at validation FAR $\le 5\%$ ($\tau_{gen} = 0.5100$)) establishes a calibrated abstain band $[0.2402, 0.5100]$:
  - **Single operating point accuracy (no abstain at FRR 5%):** **68.74%**
  - **Decision coverage outside abstain band:** **61.17%** (1,090 / 1,782 test pairs)
  - **Abstain rate:** **38.83%** (692 / 1,782 pairs deferred to manual review)
  - **Accuracy on non-abstaining pairs:** **92.29%** (TP=376, FP=53, TN=630, FN=31)

**Stronger Backbone Comparison: DINOv2 ViT-S/14 (384-d):**
Benchmarking against self-supervised DINOv2 (`dinov2_vits14`) on the exact same SOP splits demonstrates substantial gains without task-specific fine-tuning:
- ROC-AUC (All Impostors): **0.9293** (Random: **0.9788**, Hard negatives: **0.8797**)
- FAR @ FRR = 5%: **0.3081** (down from 0.4747 for MobileNetV2)
- Decision coverage: **69.53%** (Abstain rate: **30.47%**)
- Accuracy on non-abstaining pairs: **93.54%** (TP=401, FP=60, TN=758, FN=20)
- Expected Calibration Error (ECE): **0.0503** raw, **0.0428** calibrated.

**Operational Scope:**
- **What it catches:** Gross product swaps (e.g. counterfeit box containing a cheap substitute item),
  wrong product category, and visually mismatched counterfeits.
- **What it does NOT catch:** High-quality visual replicas, expert packaging counterfeits with identical
  visual design, or microscopic alterations (e.g. fine stitching, micro-print defects).
- **Graceful degradation:** If no photo is uploaded during a scan (`image_bytes` absent) or if similarity
  falls in the ambiguous abstain zone, the signal is completely ignored,
  preserving 100% functionality of the blockchain and NFC/QR identity layers.

## L-008  Single-node blockchain (no consensus)

Ganache is a single-node simulated blockchain. It has no real consensus, finality, or
peer-to-peer networking. Deploying to a real network (e.g. Polygon, Ethereum mainnet)
would require:

- Proper key management (hardware wallets or HSM)
- Gas fee strategy
- A full audit of the smart contract
- Consideration of block reorganizations affecting finality of scan logs

---

## L-009  HACP5 baseline flaw is intentional

The `nfc_rewrite_baseline.py` module deliberately reproduces the known clone-first-race flaw
of the HACP5 scheme: when a clone presents the current ID before the genuine tag, the genuine
tag is flagged as a duplicate and permanently locked out (wrong-reject rate = 100% in N=1000
trials with fixed seed 42).

This is **not a bug** — it is an accurate reproduction of the published scheme's weakness,
included as a measurable baseline.  Our counter+CMAC design (`nfc_ntag.py`) avoids this flaw
by marking the disputed tap as DISPUTED rather than blocking the tag; the genuine tag's next
tap is accepted (wrong-reject rate = 0% in same trials).

## L-011  counter+CMAC cannot block a skimmed-and-presented-first valid tap

The AES-CMAC + rolling counter scheme (`nfc_ntag.py`) is **not immune** to an
attacker who can skim an unused valid tap from the genuine tag and present it to
the server before the genuine owner does.

**Why the identity layer cannot block it:**
A valid skimmed tap `(uid, counter, cmac)` is cryptographically identical to a
legitimate first scan of that counter value.  The verifier has no way to
distinguish "genuine owner presenting counter N for the first time" from
"attacker presenting a stolen counter N for the first time."

**What the identity layer does provide:**
After the attacker's skimmed tap is accepted, the genuine tag presents the same
counter and receives a **DISPUTED** result.  This is a soft signal — not a hard
block.  The genuine tag always recovers on its next tap (genuine_recovered =
1.000 across 1 000 trials × 5 seeds in the skim-first scenario).

**How the attack is detected and blocked in the full system:**
The DISPUTED result is forwarded as a signal to:
1. **Layer 2 — scan-risk model (Phase 4):** Two accepted scans of the same
   counter from different device hashes / locations is a feature used by the
   IsolationForest and RandomForest models.
2. **Layer 3 — fusion (Phase 5):** A DISPUTED NFC tag combined with a
   suspicious scan pattern triggers the "Suspicious activity" verdict.

In other words, the counter+CMAC scheme deliberately raises a flag rather than
silently failing.  The full three-layer system is required to act on that flag.

**Comparison with HACP5:** The HACP5 baseline also accepts the skimmed tap
(skim_first clone_accepted = 1.000) but then permanently locks out the genuine
tag (genuine_rejected = 1.000, genuine_recovered = 0.000).  The counter+CMAC
scheme is strictly better: it never permanently rejects the genuine tag.

See `docs/results_race.md` for the full experiment numbers.

## L-012  RandomForest near-perfect performance and synthetic sequence-length bias

In the 5-seed evaluation on 2000 products (`data/scans.csv`, 16,213 scans), RandomForest achieves near-perfect test metrics (F1 = 0.9999 +/- 0.0002, ROC-AUC = 1.000), even on the held-out attack variant (`G_stealth_clone`).

**Feature Importance & Ablation Analysis:**
- MDI feature importance reveals that the model relies disproportionately on:
  1. `distinct_devices` (28.1%)
  2. `total_scans` (22.4%)
  3. `speed_kmh` (15.8%)
  4. `sold` (12.5%)
- In a feature ablation test, removing `total_scans` and `sold` caused the isolated F1 to collapse to 0.041.
- **Root Cause (Synthetic Sequence-Length Bias):** In the simulation, genuine journeys contain 4 to 8 lifetime hops (3 supply-chain hops + 1-4 consumer taps), whereas simulated attack sequences are appended onto genuine timelines, naturally elevating `total_scans` (reaching 8-25) and inflating `distinct_devices` beyond the typical consumer range.
- In real-world physical retail deployments, genuine products scanned by large households, store clerks, or second-hand buyers could reach higher scan counts, diminishing the separation provided by `total_scans`. Real-world deployments must normalize running counters against product age or rely more heavily on orthogonal signals (such as NFC CMAC verification and impossible velocity).

## L-013  Frontend UI is only partly tested headlessly

While the REST API and contract interactions have 129 automated tests and complete end-to-end live check coverage (`experiments/live_check.py`), the React frontend (`frontend/`) has only been verified headlessly and via Vite dev server builds. Browser-specific APIs require manual interactive testing:

1. **Camera Barcode Stream (`html5-qrcode`):**
   - Headless tests cannot grant camera permissions or stream video frames from a physical camera sensor to test QR code detection in real lighting.
2. **Web NFC Hardware API (`NDEFReader`):**
   - The Web NFC API (`window.NDEFReader`) is an experimental standard supported only on Android Chrome with physical NFC hardware. It cannot be triggered headlessly on desktop Windows.
3. **MetaMask Wallet Extension Provider (`window.ethereum`):**
   - The transaction confirmation popups, chain switching prompts, and EIP-712 / typed data signatures require an interactive browser extension with an unlocked account.
4. **Visual Layout and Responsive Breakpoints:**
   - Visual aesthetics, glassmorphism CSS, and responsive drawer animations should be visually inspected by opening `http://localhost:5173` in a desktop and mobile browser.
