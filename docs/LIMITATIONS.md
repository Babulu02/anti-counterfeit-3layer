# Known Limitations

This file documents honest limitations of the prototype. These are important to state clearly
in any paper or presentation.

---

## L-001  NFC is emulated, not physical

The NFC identity layer (Phase 2) emulates NTAG 424 DNA behavior in software.
No physical NFC chips are read or written. Consequences:

- The counter is stored in a database, not in hardware. A real NTAG 424 DNA stores the counter
  in tamper-evident hardware memory — an attacker cannot reset it without destroying the tag.
- In the emulation, a sufficiently resourceful attacker who clones the database state could
  replicate the counter. This is noted in the attack model.
- The Web NFC option (Phase 6) uses the browser's experimental Web NFC API (Android Chrome only).
  It is not available on iOS or desktop browsers as of 2026.

---

## L-002  Scan data is entirely simulated

All ML training and evaluation data (Phase 4) is generated by `experiments/simulate_scans.py`
with configurable attack mixes. Consequences:

- Reported precision/recall/F1 numbers reflect performance on synthetic data, not real-world scans.
- Real scan patterns (e.g. seasonal demand, regional distribution chains, device fingerprinting
  accuracy) may differ significantly from the simulation.
- All outputs from `run_all.py` include a header line: "NOTE: all data is simulated."

---

## L-003  Attacker adaptation

The ML model is trained on specific, labelled attack patterns (impossible travel, burst, slow clone).
A sophisticated attacker who knows the model can adapt:

- They could time cloned scans to avoid impossible-travel detection.
- They could use many distinct devices over a long period to evade burst detection.
- The NFC counter check is the strongest defense against replay; the ML layer is a second line.

---

## L-004  Privacy of location data

The system collects scan latitude/longitude to detect impossible travel. This creates
a geolocation trail per scan event. Mitigations implemented:

- Raw coordinates are never stored on-chain (only a hash, see DECISIONS.md D-007).
- The MySQL database stores raw coordinates; in production it should be encrypted at rest
  and subject to a retention policy (e.g. delete after 90 days).
- Users scanning products are not explicitly consenting to location tracking in this prototype.
  A production system must comply with GDPR / local privacy law.

---

## L-005  MetaMask is optional

The frontend supports MetaMask for manufacturer signing but falls back to backend-signed
transactions if MetaMask is not installed. This means product registration can happen without
the manufacturer's private key if an attacker compromises the backend. In production, all
`registerProduct` calls should be signed by the manufacturer's own wallet.

---

## L-006  Image-consistency signal (Phase 8) does not catch expert counterfeits

The MobileNetV2/EfficientNet-B0 embedding similarity check compares uploaded photos against
the registered reference image. It can detect obvious product swaps (e.g. a different product
in the same packaging). It does NOT detect:

- High-quality counterfeits with near-identical appearance to the genuine product.
- Packaging counterfeits where only small details differ.
- Any counterfeit where no photo is uploaded at scan time.

---

## L-007  Truffle / Ganache are discontinued

Truffle 5.11.5 and Ganache 7.9.1 are no longer maintained by Consensys (discontinued 2023).
They work for local development but may break on future Node.js versions. See VERSIONS.md
for Hardhat migration notes.

---

## L-008  Single-node blockchain (no consensus)

Ganache is a single-node simulated blockchain. It has no real consensus, finality, or
peer-to-peer networking. Deploying to a real network (e.g. Polygon, Ethereum mainnet)
would require:

- Proper key management (hardware wallets or HSM)
- Gas fee strategy
- A full audit of the smart contract
- Consideration of block reorganizations affecting finality of scan logs

---

## L-009  HACP5 baseline flaw is intentional

The `nfc_rewrite_baseline.py` module deliberately reproduces the known clone-first-race flaw
of the HACP5 scheme: when a clone presents the current ID before the genuine tag, the genuine
tag is flagged as a duplicate and permanently locked out (wrong-reject rate = 100% in N=1000
trials with fixed seed 42).

This is **not a bug** — it is an accurate reproduction of the published scheme's weakness,
included as a measurable baseline.  Our counter+CMAC design (`nfc_ntag.py`) avoids this flaw
by marking the disputed tap as DISPUTED rather than blocking the tag; the genuine tag's next
tap is accepted (wrong-reject rate = 0% in same trials).

---

## L-010  randbytes used in experiments is Python 3.9+

`random.Random.randbytes()` requires Python 3.9 or later.  The project targets Python 3.11
(see VERSIONS.md), so this is not a compatibility issue in practice.

---

## L-011  counter+CMAC cannot block a skimmed-and-presented-first valid tap

The AES-CMAC + rolling counter scheme (`nfc_ntag.py`) is **not immune** to an
attacker who can skim an unused valid tap from the genuine tag and present it to
the server before the genuine owner does.

**Why the identity layer cannot block it:**
A valid skimmed tap `(uid, counter, cmac)` is cryptographically identical to a
legitimate first scan of that counter value.  The verifier has no way to
distinguish "genuine owner presenting counter N for the first time" from
"attacker presenting a stolen counter N for the first time."

**What the identity layer does provide:**
After the attacker's skimmed tap is accepted, the genuine tag presents the same
counter and receives a **DISPUTED** result.  This is a soft signal — not a hard
block.  The genuine tag always recovers on its next tap (genuine_recovered =
1.000 across 1 000 trials × 5 seeds in the skim-first scenario).

**How the attack is detected and blocked in the full system:**
The DISPUTED result is forwarded as a signal to:
1. **Layer 2 — scan-risk model (Phase 4):** Two accepted scans of the same
   counter from different device hashes / locations is a feature used by the
   IsolationForest and RandomForest models.
2. **Layer 3 — fusion (Phase 5):** A DISPUTED NFC tag combined with a
   suspicious scan pattern triggers the "Suspicious activity" verdict.

In other words, the counter+CMAC scheme deliberately raises a flag rather than
silently failing.  The full three-layer system is required to act on that flag.

**Comparison with HACP5:** The HACP5 baseline also accepts the skimmed tap
(skim_first clone_accepted = 1.000) but then permanently locks out the genuine
tag (genuine_rejected = 1.000, genuine_recovered = 0.000).  The counter+CMAC
scheme is strictly better: it never permanently rejects the genuine tag.

See `docs/results_race.md` for the full experiment numbers.
